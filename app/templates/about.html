What This Tool Does

ThermoWatch AI takes raw thermal hotspot detections from NASA FIRMS and runs each one through three independent analysis branches (Vision, Context/Tabular, Temporal/Persistence), then fuses them into a single classification, confidence score, and 0–100 risk score, with a human-readable evidence list explaining why. See Problem Statement 26162 (SIH 2026): AI-Based Detection and Classification of Industrial Fires and Persistent Thermal Sources Using NASA FIRMS, OSM & Satellite Data.

This is a hackathon-stage prototype. Several pieces of the pipeline are necessarily placeholders for components that need real training data or pending access to stand up properly. The table below states, plainly, what is real right now, what is a placeholder, and what it becomes in production. Every one of these placeholders is also labeled directly in the UI and the API response — not just here.

Real vs. Placeholder — Component by Component
Component What's real right now What's a placeholder right now What it becomes in production
Hotspot detections (Layer 1) Live NASA FIRMS VIIRS/MODIS detections over India when FIRMS_MAP_KEY is set (free instant key). A deterministic synthetic scatter of hotspots when no key is configured, so the map is still demoable. Always labeled synthetic demo in the log and map notice. Same live FIRMS feed, always on, plus additional VIIRS NOAA-20/21 sources.
Event clustering (Layer 1) Real DBSCAN spatial clustering of detections into thermal events, run on every hotspot refresh. — Add a temporal window to the clustering (currently spatial-only per fetch).
Satellite/aerial image Real Esri World Imagery (primary) with automatic fallback to EOX Sentinel-2 Cloudless, fetched live for the clicked coordinate. A procedurally-generated placeholder image only if both real providers are unreachable — labeled synthetic_placeholder in the API response. Google Earth Engine as a third, higher-resolution Sentinel-2/Landsat provider once access is approved (interface already supports dropping it in — see app/data_sources/imagery.py).
Image processing gallery Grayscale, edge detection, and k-means segmentation are real algorithms run on the real fetched image pixels. The two "false color / heat-style" views are simulated colormaps (inferno/turbo) applied to luminance — NOT real thermal-band imagery. Real multispectral/thermal-band false color once a provider supplying those bands (e.g. Earth Engine Landsat thermal bands) is wired in.
Branch A — Vision A real call to a general-purpose multimodal LLM (Google Gemini, primary; Groq and OpenRouter as ensemble providers) with the real fetched image. The entire branch is a placeholder for a custom-trained CNN. No CNN has been trained yet — there is no labeled image dataset for this problem yet. Tagged Gemini vision (placeholder for trained CNN) everywhere. A CNN trained on a real labeled industrial-vs-natural image dataset, dropped in behind the same VisionProvider interface (see app/branches/vision.py) — no other code changes needed.
Branch B — Context/Tabular A genuinely fitted scikit-learn Random Forest; real OpenStreetMap Overpass infrastructure queries; real NASA POWER weather/soil data; real held-out evaluation (accuracy/precision/recall/F1/AUC, confusion matrix, ROC, PR curve all computed from an actual train/test split). The training labels are synthetic — generated by simple, commented rules (e.g. "closer to industry + drier soil trends industrial-like"), not real ground truth. Tagged synthetic training data. Swap generate_synthetic_training_data() in app/branches/context_model.py for a loader over a real labeled CSV with the same columns — nothing else in the branch or fusion engine changes.
Branch C — Temporal/Persistence Real rolling mean/std and z-score anomaly math, run identically regardless of data source. Once the local FIRMS archive has ≥5 distinct observation-days for a coordinate, it uses that real history. Until then, a deterministic simulated 30-day history seeded from the coordinate (same point always returns the same simulated series). Tagged simulated history in the API and UI. Same math, running on a real deep FIRMS archive pull once enough calendar time/history has accumulated in the local store.
Fusion (Layer 3) A real, transparent weighted average of the three branches' per-category probability vectors. Weights are in app/config.py (FUSION_WEIGHTS), fully config-editable. The weights themselves (40% vision / 35% context / 25% temporal) are a reasonable starting judgment call, not derived from a validation study. Weights tuned against a real labeled validation set once one exists.
Multi-Provider / Multi-Model Design

The vision branch is deliberately not a single point of failure or a single vendor's opinion: Gemini, Groq, and OpenRouter are all wired in behind the same interface and, where keys are configured, all three are queried for the same event so their answers can be shown side by side as an ensemble/agreement view. Two independent models agreeing (or disagreeing) is itself evidence for an analyst. Any provider without a configured API key shows as NO API KEY CONFIGURED in that table rather than causing an error.
